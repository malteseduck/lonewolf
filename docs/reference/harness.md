# How the harness works

The harness is everything around the code that lets AI agents (Claude Code, mainly) do most of the
work on this project while the owner keeps the decisions: the documents agents read, the rules they
follow, the scripts that check them, the hook that stops a bad commit, the skill that keeps the docs
true, the dashboard that turns each book's import into steps, and the rules for when work is handed
to a cheaper model or a separate session. This page describes it as it is and why each part is
there. The binding records are the ADRs and rulings it cites; where this page and one of them
disagree, the record wins.

## The idea in one paragraph

An agent starts every session cold. It does not remember what the owner decided last week, which
reading of a book was settled, or which files must never leave the PC. So the harness writes all of
that down in places the agent is made to read, splits it so each kind of knowledge has one home,
and backs the parts that can be checked with scripts rather than trust (spec principle 8). What
needs judgement is drafted by a script first and refined by an agent; what is the owner's call
(downloads, approving a picture, releasing, committing) is gated behind a button or an explicit ask.

## 1. The documents, and which one wins

| Layer | File | Holds | Changes when |
|---|---|---|---|
| Intent | `docs/spec.md` | What the project is for, its principles, the game rules, what the presentation must achieve | The intent changes |
| Decisions | `docs/adr/` (an ADR per topic, index in `README.md`), `docs/adr/rulings.md` (one-line rulings) | What the owner chose where there was a choice, and why | The owner decides; recorded in the same piece of work |
| Fact | `docs/reference/*.md` | How the code is now | The code changes; updated in the same piece of work |
| To do | `docs/plan.md` | Work not yet done outside the book steps | Work is found or finished (finished items leave) |
| State | `docs/book-checklist.md`, `docs/book-status.json` | Where each book stands | Generated by `tools/book_status.py`; never edited by hand |
| Instructions | `AGENTS.md` (root and four folders) | What every agent must do to work safely | A rule every agent needs is added or changes |

**Why split it this way.** Before ADR 0001, decisions were scattered through the plan, `AGENTS.md`
and the reference, nothing marked them as binding, and an agent tidying up could undo one. Now:

- The spec says what should be true, the reference what is true; a gap between them is work, not a
  contradiction to resolve by guessing.
- **ADRs and rulings are binding.** An agent never reverses or works around one without the
  owner's word in chat; if a task seems to need it, it stops and asks.
- One topic, one file: a refinement or reversal rewrites the topic's ADR in place, dated in its
  Changes list, so an agent reads the current answer, not a chain of superseded ones (git keeps the
  history). Small decisions and readings of one book's text are rulings, one row each, so they cost
  little to read. Ids are never reused.
- Records are cited as "ADR NNNN" or "ruling Rn" in code comments and docs alike, so the reason for
  a line of code is one search away.
- `AGENTS.md` holds instructions only, never state or decisions (ADR 0044): state goes stale, and
  a stale instruction read by every session is the most expensive kind of wrong.

`AGENTS.md`'s own table lists every document and what it holds; `docs/adr/README.md` says which
record a new decision goes in.

## 2. Instructions to agents

### The root `AGENTS.md`

`CLAUDE.md` at the root is one line, `@AGENTS.md`, which Claude Code expands into every session.
The instructions live in `AGENTS.md` rather than `CLAUDE.md` because other agent tools read that
name too (an `opencode.json` at the root configures one with local models). Its sections:

- **What is live**: the player is the root page and its modules; `prototypes/` and the `shared/`
  files only they use are historical (ADR 0002) and never touched, so an agent does not waste a
  session reading or fixing dead code.
- **How to run**: every Python run through uv (ADR 0037), the server, the dashboard and which of its
  buttons are the owner's alone.
- **How to test**: both suites before a commit, test first, `check_all.py` after a change to the
  books' data; the console hook for driving the page.
- **Hard rules**: no book content in the repository or in output; what of a book is committed
  (ADR 0042); downloads need the owner's go-ahead; automate only what is certain; no commit, push
  or release unasked; the look (no 3D, no pixel art, no flat colour).
- **Conventions**: classic scripts on `LW` in `shared/`, ES modules at the root, sizes in `em`,
  colours from custom properties, `esc()` on every piece of text.
- **Subagents and sessions** (ADR 0041), below.
- **Maintaining the repository**: how decisions are recorded, what a commit must bring into line,
  when to offer the maintenance pass (ADR 0044).
- **Things that will bite you**: traps found the hard way (truncating heredocs, the stock HTTP
  server cutting large files short, the iPad being served the release, stale console errors).

### Folder `AGENTS.md` files

`tools/`, `items/`, `maps/` and `assets/plates/` each have an `AGENTS.md` with the rules for work
inside that folder only, and a `CLAUDE.md` that imports it (ADR 0044). Claude Code loads a
folder's `CLAUDE.md` only once it reads a file there, so a rule lives in a folder file only if it
is not needed before then; anything needed earlier (the browser, the hard rules) stays at the root.
This keeps the root file short, which matters because every session pays to read it. The folder
files carry, for example: re-import after an importer change (tools), start an item table from the
draft and leave player choices as `todo` (items), let the owner correct OCR labels by hand (maps),
never name a colour in an image prompt and never approve a picture (fight pictures).

### The owner's memory

Claude Code also keeps a per-machine memory for this project, outside the repository: short notes
of the owner's feedback (how to judge a layout, which browser tab to leave alone, that the PC's
saves are test data). It is personal and not part of the public harness. A memory that turns out to
be a rule for one folder's work is moved into that folder's `AGENTS.md` and deleted (ADR 0044), so
it reaches every agent and every checkout, not just one machine.

## 3. Guardrails

Three things must never go wrong: licensed content leaking into the public repository, a book
being made unplayable by a misread rule, and an agent taking an action that is the owner's.

**Licensed content** (spec 3, ADR 0042). The repository is public; Project Aon's licence forbids
redistribution.

- Everything downloaded or made from a book lives in `data/projectaon/` (git-ignored); borrowed
  art in `art/`, the owner's backups in `backups/`, both git-ignored too.
- Tools print counts and ids, never prose, so nothing of a book reaches a chat log or a commit
  message through an agent reading tool output.
- What is committed about a book is our own work: item tables, map label lists and styles,
  descriptions in `about/`, and fight pictures made with AI from a text prompt alone.
- `tools/about_check.py` fails any description that shares a run of 8 words with its book;
  `tools/plates_proposals.py check` does the same for image prompts. Both are scripts, not review.
- `book.js`, the imported book, is never committed or split: even its skeleton of choices and
  fights would rebuild the book.

**Faithful rules, never trapped** (spec principles 2 and 3). Importers and drafts read only what
they can read with certainty and leave the rest as text or a `todo`; the player keeps by-hand
controls for every value. An agent is told the same: automate only what is certain.

**The owner's actions.** Gated in the instructions and on the dashboard alike: downloading a book
(the owner names it, with a rough size), importing one, approving a picture change, committing,
pushing, releasing. The dashboard's Release is the one place a push happens (ADR 0045), and only
when the owner presses it.

## 4. The commit hook

`.claude/settings.json` holds one project hook: before any Bash or PowerShell call that starts with
`git commit`, it runs `uv run --project tools python tools/docs_check.py`, and a failure blocks the
commit (ADR 0044).

**Why.** Docs drift a little with every change, and each drift misleads the next agent. Reading for
drift is costly, so the cheap, certain part runs on every commit and the costly part (the skill,
below) only when it is worth it.

`tools/docs_check.py` checks, and exits 1 on any problem:

- rulings: no id used twice, every id listed in the index's Rulings line;
- ADRs: the index lists each one, with its latest Amended date;
- citations: every "ADR NNNN" and "ruling Rn" anywhere in the repository names a record that
  exists;
- paths: every file named in `AGENTS.md` (each folder's too), the spec, the ADRs' decisions and the
  READMEs exists (git-ignored folders excepted);
- credits: every file in an asset folder is credited in its `README.txt`;
- `AGENTS.md`'s shape: its required sections present, no dates in it (ADR 0044), each folder's
  `AGENTS.md` imported by its `CLAUDE.md`;
- this page (ADR 0044): it exists, the paths it names exist, and it names in backticks every part
  read from the tree: each hook's script, each server in `.claude/launch.json`, each skill in
  `.claude/skills/` and each folder with its own `AGENTS.md`. A new part fails the commit until it is
  described here.

Its tests are in `tests/py/test_docs_check.py`; a drift found by reading that a script could have
caught becomes a new check there.

Before committing, the agent also searches the spec for the subject of every ADR or ruling the work
adds and every behaviour it changes, and brings any sentence that contradicts it into line. No
script can do that reliably, so it is an instruction, not a check.

## 5. The repo-maintenance skill

The `repo-maintenance` skill (`.claude/skills/repo-maintenance/SKILL.md`) is a periodic pass that finds and fixes drift between
`AGENTS.md`, the spec, the records, the plan, the reference, every README and the code. It runs
`docs_check.py` first, then reads what changed since the last pass, checks that `AGENTS.md` holds
only instructions, the spec against the records, the records' named functions and files against
the code, the plan and reference against what changed, the READMEs, this page against the harness
as it is (ADR 0044: the script checks each part is named, the reading that what is said of it is
true), and the owner's memory against `AGENTS.md`; then lists clean-up and runs the suites.

It draws a line between what it fixes and what it asks about: a stale path, a date out of step or a
spec sentence contradicting a record (the record wins) it fixes; anything that would change what a
record decides, a plan item that may be finished, or a file to delete it lists for the owner.

**When.** It is offered when the owner is about to release, with a rough note of what changed, and
never run unasked (ADR 0044): a small release does not deserve its cost.

## 6. Tests and checks

Each check answers one question with a script (spec principle 8; ADR 0022):

| Check | Answers | When |
|---|---|---|
| `npm test` (Vitest) | Does the JavaScript (engine, item tables, dashboard logic, offline sync) still behave? | Before every commit |
| `uv run --project tools python -m pytest` | Do the Python tools (importer parsing, book status, jobs, releases, map steps, docs check) still behave? | Before every commit |
| `tools/check_all.py` | Do the real books still import, their item tables check clean, their approved pictures hold, the offline copy have every file? | After a change to the importer, an item table, `about/` or anything the books go through |
| `tools/offline_check.py` | Does every file the page loads exist, and how big is the offline copy? | After adding or moving a file the page loads |
| `node tools/check_items.mjs <book>` | Does a book's item table agree with the book? | Item-table work (step 5) |
| `tools/about_check.py` | Does any description repeat the book's wording? | Within `check_all.py`; after writing descriptions |
| `tools/book_status.py done <book> <step>` | Is the step really done? (For steps read from files, it checks them and says NOT done, and why) | At the end of every book step |

**Why it is shaped this way.** The suites take a couple of seconds each, so agents run them every
time rather than skip them. They use stand-in data written for them, never book text, so they run
on a fresh public checkout with no books, no server and no network. Tests are written first: a new
rule starts with the failing test that states it, a bug fix with the test that shows it. They guard
the main paths as the player or owner would see them, not every line (a first pass that tested
every line took over a minute and was cut back). `check_all.py` exists because unit tests on
stand-in data cannot show that the real books still work.

The engine's rules live in `shared/` modules with their own tests, not in `main.js`; moving rules
out was done as a pure move, checked by running old and new code side by side on the same input.

## 7. The book pipeline

Each book goes through nine steps, in order (ADR 0036): 1 downloaded, 2 imported, 3 phrasings,
4 rules addendum, 5 item table, 6 test play, 7 fight pictures, 8 map, 9 illustrations.

- **The import dashboard** (`http://localhost:8766/tools/admin/`, `docs/reference/dashboard.md`)
  shows every book's steps as seals, works out each from the files on disk (or from
  `docs/book-status.json` for the judgement steps no file can show), and offers each step's buttons.
  A legend marks who does each step: a script, the owner, or Claude Code.
- **A script for every step.** Each step has a script that does what can be done with certainty and
  drafts the rest: the phrasings scan, the rules diff, the item-table draft, the picture gatherer, the
  map chain. **Drafts lean to flagging**: a false alarm costs one read, a miss costs trusting the
  draft at all; but a draft that flags everything has failed too. A script reads only signs any book
  of the series might use, never a phrase matched to one section.
- **Copy prompt** beside each judgement step gives a ready prompt (`tools/admin/prompts.js`) that the
  owner pastes into a fresh session. The prompts lean on `AGENTS.md` (the session loads it anyway) and
  carry only what is particular to the step: the book's figures, the script to start from, what to
  report, and that the script is a head start, not the whole job. A one-book miss is fixed in the
  importer or the table, never by teaching the script that book's case. Every prompt ends by marking
  the step with `book_status.py done` and saying "do not commit".
- **The sheets** (pictures, proposals, items, illustrations, icons, the map editor) put what the
  owner judges in front of them, with its context: the agent writes proposals to a file and the owner
  picks on the sheet, never from a description in chat (ADR 0008).
- **Test play is driven in Node** (`tools/walk_book.mjs`), the browser only spot-checking what Node
  cannot show: driving fights through the page cost far more for the same check.
- **Every book is offered every step whose needs it meets**, whatever its series; what holds a step
  back (the engine not having a series' rules yet) is read from the code, not from a list.

**Why.** The owner wants to take a fresh checkout and get most of a book through from the dashboard
alone, with scripts making good-enough first attempts that an agent refines when one is available.
`docs/book-checklist.md` is generated from the same status, so the state is never kept by hand in
two places.

## 8. Running and looking

- **uv for every Python run** (ADR 0037): `tools/` is a uv project with a lock file, so a fresh
  checkout rebuilds the exact tools; `tools/setup.py install all` (or the dashboard's Setup) installs
  the venv and npm packages.
- **`.claude/launch.json`** names the servers the agent's preview tools start: `lone-wolf` (the
  working copy on 8766, this PC only), `lone-wolf-lan` (the same on the network) and
  `lone-wolf-release` (the release on 8765, which the iPad is served; ADR 0045).
- **The console hook** (`__lw.game`, `__lw.render()`, `__lw.BOOKS`, `__lw.begin()`) lets an agent
  jump to a section or set a state and look, rather than click through a book.
- Agents verify in the browser by driving the page and looking at it; layout is judged by eye, not
  only by whether it fits.

## 9. Cost: subagents and sessions

The owner pays for every token, so the harness says where work runs (ADR 0041):

- **Sonnet subagents** for mechanical work big enough that it costs less there: running the importer
  or a checker and reporting figures, re-imports, copying files, applying an edit already decided,
  broad searches whose answer is a list. The brief gives exact commands, paths, what to report
  (figures and ids, not dumps) and the hard rules that touch it. A step of a call or two stays on the
  main model, since a subagent starts cold.
- **The main model** keeps judgement: what to change, the books' rules, design, judging pictures,
  and anything the owner is waiting to discuss.
- **A new session** for a different topic or independent work, Sonnet or Opus by the work, with a
  brief that stands on its own. It runs in its own git worktree and branch (under
  `.claude/worktrees/`), so two sessions never edit the same checkout; it commits only when the owner
  asks, and that commit includes merging into `main` locally, conflicts resolved keeping both sides,
  both suites run again. Nothing is pushed.

**Why.** Two sessions once worked in the main checkout at once, and a commit had to be picked apart
by hand from the other's half-done edits; sessions also committed of their own accord. Worktrees and
"commit only when asked" came of that.

## 10. From change to iPad

1. An agent makes a change, with its tests, and keeps the reference, the records and the spec in
   line in the same piece of work.
2. Both suites pass (and `check_all.py` where the books' data is touched).
3. The owner asks for a commit; the hook runs `docs_check.py` and blocks it on a problem.
4. When the owner is about to release, the agent offers the maintenance pass.
5. The owner presses Release on the dashboard: the offline check, then `tools/release.py` (a copy
   from the last commit, served on 8765), then `git push origin main` (ADR 0045). The
   iPad picks it up at its next page load.

|---|---|---|

| Reference | `docs/reference/` | How the code is now, so agents need not rediscover it |
| Plan | `docs/plan.md` | What is left outside the book steps |
| Checklist and status | `docs/book-checklist.md`, `docs/book-status.json`, `tools/book_status.py` | Where each book stands, worked out from files, never kept by hand |
| Root instructions | `AGENTS.md`, `CLAUDE.md` | What every agent needs to work safely, loaded into every session |
| Folder instructions | `tools/`, `items/`, `maps/`, `assets/plates/` `AGENTS.md` + `CLAUDE.md` | Rules for one folder's work, loaded only when that work starts |

| Docs checker | `tools/docs_check.py`, `tests/py/test_docs_check.py` | The certain part of drift, checked by script |
| Maintenance skill | `.claude/skills/repo-maintenance/` | The judged part of drift, at release time |
